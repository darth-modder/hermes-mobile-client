# Connecting: toolchain and dev-loop recipes

This machine has no `ANDROID_HOME` / `JAVA_HOME` set globally, and we do not set them globally
either. Every command below sets them per-invocation.

## Build path: WSL2, not Windows Gradle (decision D3)

**Local Gradle builds fail on this Windows machine, independent of JDK choice** — every JDK from
17 through 25 hits `java.io.IOException: Unable to establish loopback connection` /
`SocketException: Invalid argument: connect` while Gradle's launcher opens an `AF_UNIX` wakeup
pipe for its daemon selector, root-caused (not just worked around — see M01's Blocker section for
the full trace) to this specific Windows build (10.0.26200) rejecting that connect below the JVM.
Decision D3 (`project-planning/DECISIONS.md`) accepts this and keeps WSL2 as the supported local
build path; do not spend further effort on the Windows failure. `npm run prebuild` and
`expo-doctor` still run fine from Windows (they don't invoke Gradle) — only the actual
`./gradlew assembleDebug` / `assembleRelease` step needs WSL2.

### WSL2 setup (Ubuntu-26.04, already installed on this machine)

A Linux kernel doesn't have the Windows AF_UNIX bug, so builds run there against the same
`D:\Stuff\...` project tree mounted at `/mnt/d/...`. Set up entirely in user space (no `sudo` —
interactive sudo isn't available non-interactively):

- `~/.jdks/temurin-21` — Temurin JDK 21 for **linux-x64**, downloaded + checksum-verified against
  Adoptium's own checksums, `tar -xzf`'d directly.
- `~/Android/Sdk` — a **separate, Linux-native** Android SDK — the Windows SDK's `build-tools`
  binaries (aapt2, etc.) are Windows PE executables and cannot run under Linux, so this cannot be
  the same directory as `D:\Software\Android-SDK`. Installed via Google's
  `commandlinetools-linux-9862592_latest.zip`, then
  `sdkmanager "platform-tools" "build-tools;36.0.0" "platforms;android-37.0"` — matching the
  Windows SDK's versions. This SDK has no `emulator` package installed — the emulator itself runs
  on the Windows side (Android Studio's `hermes-test` AVD, `emulator-5554`); WSL2 only builds and
  installs onto it via `adb`.
- `~/.nvs/node/v24.16.0` — Node 24.16.0 for linux-x64, checksum-verified against nodejs.org's own
  `SHASUMS256.txt`. Gradle's `settings.gradle` shells out to `node` to resolve Expo's autolinking
  config, so a missing Node fails the build at settings-evaluation, before Gradle compiles
  anything.

`android/local.properties` (git-ignored, regenerated by `expo prebuild`, never committed) must be
rewritten by hand after every prebuild to point at the **WSL** SDK, since prebuild (run from
Windows, where `ANDROID_HOME` is unset) doesn't write it:

```
sdk.dir=/home/you/Android/Sdk
```

### Running a WSL command from this environment's git-bash

`wsl.exe` invocations need `MSYS2_ARG_CONV_EXCL="*"` (or the Bash tool's `MSYS_NO_PATHCONV=1`),
or MSYS2's automatic POSIX-path rewriting mangles every Linux-style argument (`/home/you/...`
silently becomes `C:/Program Files/Git/home/you/...`). Multi-statement inline `bash -lc '...'`
strings are unreliable across that boundary regardless (variable assignments can come through
empty) — always run a WSL build/check as a script file:

```bash
MSYS2_ARG_CONV_EXCL="*" wsl -d Ubuntu-26.04 -- bash /mnt/c/path/to/script.sh
```

with the script itself setting up `PATH`/`ANDROID_HOME`/`JAVA_HOME` and `cd`-ing into
`/mnt/d/Stuff/Code/git/hermes-android/android` before invoking `./gradlew`.

### Build cost

`./gradlew assembleDebug --no-daemon` takes **~20–32 minutes** the first time from a clean Gradle
cache (slower — not broken — because native-library hard-linking falls back to a slower copy
across the Windows/WSL filesystem boundary at `/mnt/d/...`); faster once `~/.gradle` is warm.

## SDK / JDK locations on the Windows side (this machine)

- Android SDK: `D:\Software\Android-SDK` (platform-tools, build-tools 36.0.0, platforms/android-37.0,
  emulator). A second SDK at `C:\Program Files (x86)\Android\android-sdk` has cmdline-tools and
  android-35/36 — only needed if Gradle demands an older platform than 37.
- JDK: Android Studio's bundled JBR at `D:\Software\Android\jbr` (OpenJDK 25) — only relevant if
  ever re-attempting a Windows-side build; the WSL2 path above uses its own JDK 21 instead.
- `adb`: `D:\Software\Android-SDK\platform-tools\adb.exe` — this is what actually talks to the
  emulator/device; WSL2's own `adb` (under `~/Android/Sdk/platform-tools`) talks to the same
  `adb` daemon over the loopback port it shares with Windows, so either one sees `emulator-5554`.

## Per-command environment (PowerShell, for `npm run prebuild` / `expo-doctor` / `adb` from Windows)

```powershell
$env:ANDROID_HOME = 'D:\Software\Android-SDK'
$env:JAVA_HOME = 'D:\Software\Android\jbr'
$env:Path = "$env:ANDROID_HOME\platform-tools;$env:JAVA_HOME\bin;$env:Path"
```

Run this in the same shell/session before `npm run prebuild` or any `adb` invocation from
Windows. `npm run android` / `npm run apk:release` (which invoke Gradle) don't work from Windows
at all per the Build path section above — build via the WSL2 script instead, then `adb install`
the resulting APK from either side.

## Verify a device is attached

```powershell
& "D:\Software\Android-SDK\platform-tools\adb.exe" devices
```

Plug in a phone with USB debugging enabled, or start an emulator from Android Studio, before
building.

## Dev loop

```powershell
npm install
npm run prebuild   # expo prebuild --platform android --clean (Windows is fine for this step)
```

then rewrite `android/local.properties` to the WSL SDK path (see above) and, via WSL2:

```bash
cd android && ./gradlew assembleDebug --no-daemon
```

then install and launch from Windows (or WSL2 — same `adb` daemon):

```powershell
& "D:\Software\Android-SDK\platform-tools\adb.exe" install -r android\app\build\outputs\apk\debug\app-debug.apk
& "D:\Software\Android-SDK\platform-tools\adb.exe" shell am start -n com.nousresearch.hermes.mobile/.MainActivity
npm run start       # expo start --dev-client — Metro only, once the dev-client is installed
& "D:\Software\Android-SDK\platform-tools\adb.exe" reverse tcp:8081 tcp:8081
```

## Connecting the app to a local `hermes serve`

`hermes serve --host 127.0.0.1 --port 9119` binds loopback only. The server rejects WebSocket/
REST peers that are not loopback when bound to `127.0.0.1`, and any non-loopback `Host` header
forces gated auth — so for local dev we forward the phone's own loopback to the host's loopback
instead of using the host's LAN IP:

```powershell
& "D:\Software\Android-SDK\platform-tools\adb.exe" reverse tcp:9119 tcp:9119
```

With the reverse tunnel in place, the app on the phone can dial `http://127.0.0.1:9119` /
`ws://127.0.0.1:9119` exactly as if it were running on the host — the peer-address check on the
server sees a loopback connection, and `?token=` mode (dev only) works without gated auth. This
is why token-mode is dev-only: it only works when the server considers the peer to be loopback,
which in production means a real TLS-terminated remote host with the password or Portal OAuth
flow instead (see the auth matrix in `project-planning/implementation-plan/README.md`).

Read the session token the way the desktop app does — see
`../hermes-agent/apps/desktop/electron/dashboard-token.ts` and `hermes_cli/web_server.py` around
`_SESSION_TOKEN` / `HERMES_DASHBOARD_SESSION_TOKEN` in the upstream checkout. Never paste the
token into a commit, log, or milestone file.

## Connecting to a gated `hermes serve` (M04: password login)

`hermes serve --host 0.0.0.0 --port <port>` binds all interfaces, which flips `auth_required` on —
a non-loopback bind always gates. The Android emulator reaches the host machine at the special
alias `10.0.2.2` (not `127.0.0.1`, and not the host's real LAN IP), so point the app's connect
screen at `http://10.0.2.2:<port>`. No `adb reverse` needed — the emulator's virtual NIC routes
`10.0.2.2` to the host directly.

The bundled `basic` username/password provider can be configured non-interactively for dev/test —
`hermes dashboard auth setup` is interactive-only, but the provider reads
`HERMES_DASHBOARD_BASIC_AUTH_USERNAME` / `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD` env vars directly
(env wins over `config.yaml` when non-empty; see `plugins/dashboard_auth/basic/__init__.py` in the
upstream checkout):

```bash
HERMES_DASHBOARD_BASIC_AUTH_USERNAME=tester HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=<generated> \
  hermes serve --host 0.0.0.0 --port <port>
```

Generate the password into a scratch file outside the repo the same way as the session token —
never paste it into a commit, log, or milestone file.
