## D21.3.1 — approval path (`fix/approval-path`)

**What's real and committed.** The root-cause hypothesis (a scroll request racing the new card's
header measurement, landing the list ~391px short) is fixed in `src/chat/Transcript.tsx` +
`src/chat/scroll-to-bottom.ts`, with a regression test proven against a naive near-miss
implementation first (fails), then the real fix (passes 5/5). Full suite 787/787,
typecheck/lint/prettier clean. Commit `adddc20`, plus a follow-up report-correction commit
`07266a5`. Both pushed to `origin/fix/approval-path`.

**What's not reached, and why it matters.** Every live-device criterion in the original brief — the
10-of-10 approval-race repro across two themes, sudo/secret/clarify driven live, all four buttons
with a wire trace, the five-part overlap-glitch variation matrix — is **not reached**. This session
first misdiagnosed the emulator as unbootable (a WSL2-vs-Windows environment mixup, corrected
mid-round); once corrected, the emulator, the branch dev client, and Metro were all confirmed
working end to end. What stopped the live work at that point was a **permission decision, not a
technical wall**: getting a real model on the wire needs a throwaway gateway, which needs a model
API key copied out of the user's real `.env` — an action `fix/approval-path`'s own session was
correctly refused by its permission classifier (Credential Materialization), and it declined to use
a workaround another session had set up for a related but distinct purpose, on cross-session
permission-laundering grounds. That decision stands; see the source report's §6.5 for the full
reasoning.

**The one finding that matters most for whoever runs the live pass next:** a prior same-day session
left an evidence trail (`D:\Stuff\hermes-android-field\fix-approval\`) showing a second approval
card's buttons absent from the accessibility tree 40–104 seconds after the server sent
`approval.request`, on a build that already had this exact fix in its working tree. This is read
evidence, not something this round generated or can attribute with certainty — but it means the fix
should be treated as **proposed, not confirmed closed**, until someone re-runs the exact
reject-then-second-request sequence live and watches the wire trace and the tree at the moment the
second request lands.

## D21.3.2 — upstream re-pin (`fix/upstream-repin`)

**The break the task was filed against was not reproducible** — `CronBlueprint`/
`CronBlueprintField` had already been turned into local types in `src/api/cron.ts` before this
round started (an earlier "M15 round 1" change, predating this branch), because upstream's own
desktop app never declared a type under that name at any commit. Verified independently this round:
grep confirms neither file imports these names from `src/upstream/`, and `npm run check` is fully
green (74 test files, 782 tests, 52 Python plugin tests, eslint, prettier — all clean).

**Sync is idempotent.** Two consecutive `node scripts/sync-upstream.mjs` runs produced identical
output and zero `git diff`, confirming the working tree already matched a fresh sync against pin
`ee84ccd8bd13d0025e98bb6be8ceb93303e3bdff`.

**One real bug found and fixed**, outside the cron path: `scripts/generate-icons.mjs`'s output
(`src/lib/icons.ts`) had a stale provenance comment — the re-pin commit updated `UPSTREAM.json` and
`src/upstream/` but never re-ran this generator, so the file's own header claimed the *old* pin.
Content was byte-identical (no icon renamed or added upstream), but the comment was lying about its
source commit. Fixed by re-running the generator; `npm run check` re-confirmed green after. Commit
`00c466e`, pushed to `origin/fix/upstream-repin`.

**Drift across the five named areas, all checked:** gateway events unchanged; RPC shapes in
`types/hermes.ts` changed (new optional fields on `SessionMessage`/`UsageStats`/`ContextBreakdown`,
two fields removed from `MoaConfigResponse`) but nothing in this app reads any of them, confirmed by
grep; theme presets unchanged; `en.ts` gained two new label groups (`sessionImport`,
`agents.steer*`) for desktop features this app's UI doesn't implement yet — a product gap, not a
build gap, named and left alone; the icon alias module was the stale-comment bug above, now fixed.
This was a static/type-level check only (no Android emulator or device was used for D21.3.2 — the
task itself is about not breaking the build, not about device behavior).
